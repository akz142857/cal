本方案定义 Cal 仓库的评审对象、角色、流程、检查清单、严重性分级与放行规
则。它同时覆盖两条轨道：

- **轨道 A｜里程碑评审**：一次性、成建制的深度评审，在"冻结协议前"和
  "消费一次性留出前"这两个不可逆节点强制执行；
- **轨道 B｜常态评审**：每个 PR 的轻量清单，成本控制在 30 分钟内。

评审的目标不是"代码好不好看"，而是**保证已发表证据不被污染、保证下一次
一次性留出的消费是值得的**。Cal 的核心资产是证据链而不是代码，因此本方
案的优先级排序始终是：科研完整性 > 冻结与锁一致性 > 代码正确性 > 工程质量。

## 0. 为什么现在需要这份方案

当前仓库正处在一个典型的"评审窗口"上：

- V2-L0 V8 的**唯一留出已于 2026-07-28 消费并失败**（24 门中 3 门失败，
  `decision=stop_and_report`），该留出不可重试；
- `docs/experiments/V2_L0_PERMANENCE_DIAGNOSIS_AND_PREREGISTRATION_DRAFT.md`
  自己声明为"**非冻结草案，供评审**"，明确等待评审（含潜在第三方评审）后
  才由 runner 生成冻结 `*.json` + `.sha256` + `locked_source_sha256`；
- 与之配套的随机化永久性机制（`cal/model/stochastic_motion_filter.py`、
  `cal/evaluation/stochastic_permanence_*.py`、`permanence_*.py`、
  `randomized_occlusion_world.py`，共 14 个新模块，含 2 个 `_` 前缀基线）
  已落地并通过开发门，但**尚未进入任何 source lock**。

也就是说：**下一次冻结与下一次留出消费之前，是最后一个"改动仍然免费"的
时刻**。本方案就是为这个时刻服务的。

## 1. 评审范围

### 1.1 在范围内

| 层 | 对象 | 主要风险 |
| --- | --- | --- |
| L1 科研完整性 | 预注册草案、门定义、seed 角色划分、停止规则、对照组设计 | 事后调参、捷径、留出泄漏 |
| L2 冻结与锁 | `experiments/*.json` + `.sha256` + `locked_source_sha256`、修订链 | 锁覆盖不全、静默失效、在位修改历史产物 |
| L3 代码正确性 | `cal/model/`、`cal/evaluation/`、`cal/env/` 的行为正确性 | 指标算错、对照组构造错、状态泄漏 |
| L4 复现与工程 | 测试、CI、provenance、`results/INDEX.json`、依赖 | 本地通过而 CI 不跑、结果无法归因 |
| L5 文档一致性 | `README.md`、`RESEARCH_STATUS.md`、`docs/experiments/*.md`、dashboard 文案 | 结论过期、口径不一致、宣称超出证据 |

### 1.2 明确不在范围内

- 不评审"研究方向是否值得做"——那属于 `docs/RESEARCH_PLAN_V2.md` 的层面；
- 不评审已消费留出的**结果数值**是否"应该更好"——已消费即终局，评审只
  检查其记录是否忠实；
- 不做性能优化建议，除非它影响 `resource_limits` 门的判定；
- 不重写历史 `calmodel/...` 路径（见 `CLAUDE.md`，那是历史证据）。

## 2. 角色与独立性要求

| 角色 | 职责 | 独立性要求 | 适用轨道 |
| --- | --- | --- | --- |
| 作者（Author） | 提交自查表、复现命令、影响面声明；**承担举证责任** | — | A/B |
| 主评审（Reviewer） | 执行 R1–R4 全部清单，出具报告 | 未参与被评审改动的编写 | A/B |
| **红队（Red Team）** | 在 R2 尝试**构造一个不依赖目标机制、却能通过冻结门的方案**；在 R3 尝试构造反例输入 | 不看作者的辩护材料，只看协议 + 代码 | **仅 A** |
| 对抗验证者（Adversary） | 仅针对**候选发现**做独立复核，判定 CONFIRMED / PLAUSIBLE / REJECTED | **不知情**：不告知作者结论、不告知其他验证者的判定 | 仅 A |
| 裁决人（Adjudicator） | 仅在红队与作者对同一事实判断相持不下时介入 | 与作者、红队均不同人 | 仅 A，且仅在争议时 |
| 留出守门人（Gatekeeper） | 授权/拒绝一次性留出的消费 | 必须与作者不同人 | 仅 A |

### 2.1 为什么是"不对称红队"而不是"正反方辩论"

**不设对称辩论**，理由有三：

1. **正方已经天然存在**。作者的提交本身就是完整的正方陈述。再指派一个人
   "论证它应该通过"，不产生新信息，只产生角色偏见与责任稀释——通过与否
   将变成两套说辞的比拼，而不是证据的比拼。
2. **辩论的产物是说服力，评审需要的是证物**。本项目历次真正有价值的发现
   （方向丢失、`MAX_FILTERS` 永久耗尽、跨轴污染、门名实不符）全部是**可
   复现的事实**，不是观点。评审格式应当奖励"跑出一个数"，而不是奖励
   "讲得更有道理"。
3. **对称辩论对 agent 评审尤其不利**。若由 agent 承担评审，对称的立场分配
   会放大迎合与锚定；而"证伪型"任务有客观成功判据，可靠得多。这也是本方案
   在 R3 沿用"不知情验证者"的原因——它本来就是不对称的（只让它试图**驳倒**
   发现）。

**改为不对称结构**：把对抗压力集中在**举证责任**上，而不是分配到两个对立
的辩手身上。

| | 正方 | 反方 |
| --- | --- | --- |
| 谁 | 作者（天然） | 红队（R2）+ 不知情验证者（R3） |
| 要证明什么 | "门被通过，是因为目标机制起作用" | "门可以被通过，而目标机制没起作用" |
| 举证责任默认落在 | **正方** | — |
| 相持不下时 | 判**不通过** | — |

**默认判不通过**这条是核心：一次性留出是不可再生资源，误放行的代价（烧掉
留出、污染证据链）远大于误拦截的代价（多花几天）。V7 的先例已经证明了这
个方向——那次是在 source lock 已发布之后才由独立评审发现崩溃恢复缺陷，导致
该锁**永久不得开封**。

### 2.2 红队的成功判据（可证伪，不是"提意见"）

红队不是"挑刺的人"，它有一个明确的、可判定的胜利条件：

> **在只使用 development / calibration seed 的前提下，构造一个不实现目标
> 机制的方案，使其通过冻结协议中的全部门。红队一旦成功，协议即判定失败。**

这个设定直接对准了本项目已被证实的最大失败模式。V8 的根因不是代码 bug，
而是**环境本身提供了跨 seed 不变的几何捷径**：遮挡屏固定在 `x=10`、门洞固定在
`row 12`、隐藏物体方向仅由 seed 奇偶决定，于是"被遮 k 步后在哪个格子"是
`(hidden_steps, seed 奇偶)` 的确定函数，raw sensor 的查询 one-hot 配合固定
布局就足以通过 permanence 门——**并且真的通过了，还反超了正式模型**。这类
问题没有任何 checklist 能可靠地发现，只能靠一个以"打穿它"为目标的角色。

本轮针对随机化遮挡世界的**红队攻击清单**（每条要么给出攻击成功的数字，
要么给出攻击失败的证据）：

- [ ] **纯位置先验攻击**：只用查询格 one-hot（丢弃全部占据栅格）训练线性
      探针，看 permanence 门能到多少。若接近阈值，说明门测的是布局记忆；
- [ ] **跨 seed 不变量攻击**：度量 `(hidden_steps, seed 派生量)` 与答案之间
      的互信息；若显著非零，随机化不充分；
- [ ] **负样本几何攻击**：沿用 V8 的负样本构造（取最近的不可见非静态格），
      检查正负样本是否仅靠曼哈顿距离即可分开；
- [ ] **平凡基线攻击**：raw sensor / assume-all-visible / no-action 三个对照
      是否可能**反超**正式模型（V8 正是死在这里）；
- [ ] **对照组不可构造攻击**：尝试证明某个冻结对照在目标 split 上**构造不
      出来**。V5 留出就是这样中途停止且不可重试的，这条必须在冻结前跑通；
- [ ] **门名实不符攻击**：逐门核对"门名宣称检查的对象"与"代码实际比对的
      对象"是否一致（先例：`v1_development_matches_v1_protocol` 实际只核对
      文件自己声明的字段）；
- [ ] **锁绕过攻击**：在不触发任何哈希校验的前提下，改变门的判定结果——
      §4.3 的 G1–G4 都是现成的绕过路径；
- [ ] **资源门规避**：找出未计入 `estimated_mac_per_step` 的开销。

红队的每一条攻击，无论成败，都要以"命令 + 数字"的形式进报告；**攻击失败
本身就是本轮最有价值的正面证据**，比作者声明"我们已经随机化了"强得多。

**近失分级**（攻击未完全成功时的处置）：胜利条件要求"通过全部门"是刻意
的——对照门存在的意义就是抓捷径，捷径被对照门抓住恰恰说明协议在工作。但
近失的严重性差异必须分级记录：

- 作弊方案通过**全部主门**、仅被**一个**对照门拦下 → 记 **P1**（协议对该
  捷径只有单点防御，该对照门一旦有实现 bug 即全线失守）；
- 通过全部主门、被**多个**对照门独立拦下 → 记 P3，作为协议稳健性的正面证据；
- 在某个主门上达到阈值的 90% 以上 → 记 P2，说明该门的判别力主要不来自
  目标机制，阈值余量需要在报告中说明。

### 2.3 成本控制

红队只在**轨道 A**、且只在两个不可逆节点前强制启用：**冻结协议前**、
**消费一次性留出前**。轨道 B（日常 PR）不设红队，只保留 §3.2 的三问。
裁决人只在争议发生时才存在——不争议就不需要这个角色。

### 2.4 角色实例化（单人项目的现实约束）

`git log` 证实本仓库只有**一位人类贡献者**。若把"必须与作者不同人"照字面
执行，轨道 A 永远无法启动——这不是假设风险，是当前事实。因此明确规定角色
如何实例化：

| 角色 | 实例化方式 | 依据 |
| --- | --- | --- |
| 作者 | 人类（或产出该改动的 agent 会话） | — |
| 主评审 | **独立 agent 会话**：新上下文，不含作者会话的推理过程 | 2026-07-26 复核即此模式，产出 6 个 CONFIRMED bug |
| 红队 | 独立 agent 会话：只喂协议 + 代码，不喂作者叙述 | 同上 |
| 对抗验证者 | 每个候选发现一个独立 agent 会话 | 同上（"不知情验证者"） |
| 裁决人 | **人类** | 判断责任不可下放 |
| Gatekeeper | **人类** | 消费留出是不可逆决策，必须由人签署 |

三条边界：

- **独立性的最低标准是上下文隔离**：评审/红队会话不得继承作者会话的对话
  历史、草稿或中间结论。同一个人类先后扮演作者和裁决人是不可避免的，但
  两次决策之间必须隔着书面的、双方独立产出的证据（攻击台账、验证判定）；
- **agent 评审的产出必须落到可复核的命令与数字**，人类抽查其中任意一条都
  能复现——这是单人项目里"独立性"的实际替代物：不是换一个人，而是换成
  **任何人都能重跑的证据**；
- 若未来有第二位人类贡献者或外部评审者加入，人类角色优先于 agent 角色。

### 2.5 通用约束

**不知情原则**（沿用 2026-07-26 复核的做法）：每个候选发现派一个独立的验证
者，只喂给它"发现描述 + 相关代码"，不喂给它作者的辩解或其他发现。只有
CONFIRMED / PLAUSIBLE 的发现进入报告。这是为了避免评审者被作者叙事锚定。
红队同理：不向红队提供作者的辩护材料。

**留出隔离硬约束**：评审过程中的任何人（**尤其是红队**），在留出被正式
授权消费之前，都**不得**运行任何会读取留出 seed 段的命令。评审只能使用
development / calibration seed。违反此约束等价于烧毁该留出。红队"打穿门"
的尝试必须在 development split 上完成。

## 3. 流程

### 3.1 轨道 A：里程碑评审（冻结前 / 留出消费前）

```
R0 准入 → R1 静态一致性 → R2 科研完整性 ┐
                                        ├→ R4 复现与工程 → R5 判定与归档
                          R3 代码正确性 ┘
          红队（§2.2）与 R2/R3 并行独立进行，不共享中间结论
```

R2/R3 与红队**并行且互不通气**：主评审走清单（覆盖面），红队走攻击
（深度）。两者在 R5 汇合，冲突项交裁决人。这样安排是因为清单式评审与
证伪式评审的盲区不同——清单查"该做的做了没"，红队查"做了也没用"。

**R0 准入检查**（不通过则直接退回，不消耗评审工时）

- [ ] 作者提交了影响面声明：本次改动触碰了哪些 `locked_source_sha256` 覆盖
      的文件、哪些已发表结果的产生机制、哪些留出的前置条件；
- [ ] `uv sync --extra dev && uv run pytest` 在作者环境全绿，并附命令输出；
- [ ] 工作树干净（`git status` 无未提交改动），或已说明为何不干净；
- [ ] 若本轮涉及冻结：草案文档已写明假设、固定指标、对照组、split 角色、
      停止规则——五者缺一不得进入 R2。

**R1 静态一致性**（机械可执行，先做，便宜）

```bash
# 1. 每个协议 JSON 与其 .sha256 边车是否一致
#    注意：边车存在两种路径写法（30 份写裸文件名，CAL_NAMESPACE_MIGRATION.sha256
#    写 experiments/ 前缀），所以不能简单用 `cd experiments && shasum -c *.sha256`
python3 - <<'PY'
import hashlib, pathlib
bad = 0
for s in sorted(pathlib.Path("experiments").glob("*.sha256")):
    want, name = s.read_text().split()
    target = pathlib.Path(name) if pathlib.Path(name).exists() else s.parent / pathlib.Path(name).name
    if not target.exists():
        print(f"MISSING  {s.name} -> {name}"); bad += 1; continue
    if hashlib.sha256(target.read_bytes()).hexdigest() != want:
        print(f"MISMATCH {s.name} -> {name}"); bad += 1
print("sidecars OK" if not bad else f"{bad} sidecar problem(s)")
PY

# 2. locked_source_sha256 声明的每个文件当前实际哈希（按协议版本自动分类）
python3 - <<'PY'
import hashlib, json, pathlib, collections
rows = collections.defaultdict(list)
for p in sorted(pathlib.Path("experiments").glob("*.json")):
    try: d = json.loads(p.read_text())
    except Exception: continue
    locked = d.get("locked_source_sha256")
    if not isinstance(locked, dict): continue
    for src, want in locked.items():
        f = pathlib.Path(src)
        if not f.exists():
            rows[p.name].append(("MISSING", src)); continue
        if isinstance(want, str) and hashlib.sha256(f.read_bytes()).hexdigest() != want:
            rows[p.name].append(("DRIFT", src))
for name in sorted(rows):
    print(f"{name}: " + ", ".join(f"{k}:{v}" for k, v in rows[name]))
if not rows: print("all locked sources match")
PY

# 3. 结果索引可重建且无孤儿
uv run cal-index --results results && git diff --stat results/INDEX.json
```

R1 的产出是一张"当前锁状态表"。**MISSING / DRIFT 都不必然是错误**，评审要
做的是把每一条归类为"已修订 / 待修订 / 违规"。以 `4e0c7c2` 的实测为例：

| 现象 | 涉及协议 | 正确归类 |
| --- | --- | --- |
| MISSING `calmodel/...` 路径 | M1–M3 确认协议 V1、V2 | **已修订**。这是 `calmodel`→`cal` 重命名前冻结的历史链接，按 `CLAUDE.md` 不得改写 |
| DRIFT `entity_graph.py`、`v2_m1_m3_confirmation.py` | M1–M3 确认协议 V3–V6 | **已修订**。V3–V6 是被 V7 取代的修订链，漂移是预期的 |
| 无漂移 | M1–M3 确认协议 **V7**（当前生效） | 锁健康 |
| 边车全部一致 | 全部 31 份 | 健康 |

由此也暴露一条真实的文档不一致：`CLAUDE.md` 称当前生效协议为
`..._PROTOCOL_V3.json`，而实际生效的是 **V7**
（`frozen_after_v6_entity_graph_confidence_adaptive_gating_extension`）。按
§8 分级这是 P2，应在本轮一并更正——它会让新贡献者查错锁。

## 5. L3 代码正确性清单

采用 2026-07-26 已验证有效的**八角度探测法**，每个角度独立扫一遍改动面：

1. **逐行**（line-by-line）：新代码本身的逻辑；
2. **被删行为**（removed-behavior）：删掉/改掉的分支原本在保护什么；
3. **跨文件**（cross-file）：调用方与被调方的假设是否仍然一致；
4. **复用**：是否重复实现了已有工具（`v2_artifacts`、`provenance`、seed 注册表）；
5. **简化**：是否有可删的死代码（历史上 `retired` 属性即死代码，且掩盖了
   容量永久耗尽的 bug）；
6. **效率**：是否影响 `estimated_mac_per_step` 与资源门；
7. **高度**（altitude）：抽象层次是否与周边一致；
8. **约定**：`@dataclass(frozen=True, slots=True)`、seed 按角色划分、注释语言
   随文件既有语言。

针对本项目的**高频缺陷模式**，作为必查项固化下来：

- [ ] **默认值陷阱**：任何"世界版本 / 协议版本 / split 角色"类参数**不得有
      默认值**。历史上 `_episode()` 的 `environment_version` 出现过 2 / 1 / 3
      三处不一致的默认值；不确定该用哪个时应当报错，而不是给一个可能错的答案；
- [ ] **状态跨实体污染**：共享的学习器/缓存必须用复合键（曾出现 `PauseLearner`
      仅用裸坐标做 key，导致不同轴的实体互相读到对方的规律）；
- [ ] **容量上限的行为**：任何 `MAX_*` 上限被打满时的行为必须是显式的（LRU
      淘汰或报错），不得是"静默拒绝新建"；
- [ ] **构造函数初始化完整**：算出来的初值必须存进 `self`（曾出现方向 `d`
      算对但没存，靠 `getattr(..., 1)` 回退到错误默认）；
- [ ] **门的名实相符**：门的名字所宣称的检查，与其实际比对的对象一致（曾
      出现 `v1_development_matches_v1_protocol` 只核对文件自己声明的字段）；
- [ ] **真值不入模型**：body mask / object mask / 可见性掩码等评估专用状态
      只在评估期由确定性重放生成，不出现在任何模型输入路径上；
- [ ] **探针梯度不回流**：probe 的优化器参数列表不含被冻结模型的参数。

### 6.2 CI 覆盖（真实的静默失败面）

CI (`.github/workflows/tests.yml`) 用 8 个 matrix group **按文件名分片**执行，
其中两组用 glob：`tests/test_[a-i]*.py` 与 `tests/test_[m-u]*.py`，其余为
显式清单。因此：

- 首字母落在 `j`/`k`/`l` **或 `v`–`z`** 的新测试文件，只要没被加进显式清单，
  **会静默不被 CI 执行**，而本地 `uv run pytest` 照跑不误（今天 `test_v2_*`

- 检查命令（`4e0c7c2` 实测输出为 `CI covers all test files`，即当前无缺口，
  但该性质**不是自动维持的**，每次新增测试文件都要重跑）：

```bash
# 列出 CI 分片实际覆盖的文件 vs 仓库中的全部测试文件，取差集
uv run python - <<'PY'
import glob, pathlib, yaml
wf = yaml.safe_load(pathlib.Path(".github/workflows/tests.yml").read_text())
pats = []
for e in wf["jobs"]["pytest"]["strategy"]["matrix"]["include"]:
    pats += e["tests"].split()
covered = {p for pat in pats for p in glob.glob(pat)}
allt = set(glob.glob("tests/test_*.py"))
missing = sorted(allt - covered)
print("NOT RUN IN CI:", *missing, sep="\n  ") if missing else print("CI covers all test files")
PY
```

- [ ] 上述差集为空；
- [ ] 新增的长耗时评估在 CI 30 分钟超时内，或已明确标记为不进 CI 并说明
      如何离线验证。

## 8. 严重性分级与放行规则

| 级别 | 定义 | 处置 |
| --- | --- | --- |
| **P0** | 会污染证据链：留出泄漏、在位修改历史产物、门的实现与冻结定义不符、真值进入模型输入 | **阻断**。不修不得冻结、不得消费留出 |
| **P1** | 会使本轮结论不可信：对照组构造错误、指标算错、存在未被排除的捷径、锁未覆盖本轮机制 | **阻断**，除非评审组书面接受并写入报告的"已知限制" |
| **P2** | 影响可复现性或未来正确性：默认值陷阱、CI 不覆盖、资源估算漏项、文档口径不一致 | 可 `pass_with_conditions`，须在冻结前或下一个 PR 内修复并登记 |
| **P3** | 工程质量：命名、重复实现、死代码 | 记录，不阻断 |

**放行规则（decision rule）**

- `block`：存在任一未解决的 P0，或存在未被书面接受的 P1，**或红队任一攻击
  成功**（红队成功即证明门可以在机制不起作用时被通过，等价于 P0）；
- **相持不下时判 `block`**：红队与作者对同一事实判断无法在证据层面解决时，
  默认取阻断——举证责任在正方（§2.1）。特别地，"我们认为这个捷径在留出上
  不会发生"不构成证据，只有在 development split 上跑出的数字才是；
- `pass_with_conditions`：P0=0、P1=0，存在 P2 且每条 P2 都有责任人与期限；
- `pass`：P0=0、P1=0、P2=0。

**冻结与留出的额外要求**：只有 `pass` 才能生成冻结协议；只有 `pass` 且
Gatekeeper 单独签署，才能授权消费一次性留出。历史上 V7 就是在"已发布
source lock 之后"才由独立评审发现一次性崩溃恢复缺陷，因此该锁**永久不得
开封**——这条先例说明：**锁不是评审的终点，评审必须发生在锁之前**。

### 9.1 报告的更正规则

评审报告是历史产物，默认**不可在位修改**：更正以新增"补充评审"文档的形式
追加，并在两份文档之间互相引用。

这条曾是一刀切，实践中发现过严——一个明显的章节号笔误逼出一整份补充文档，
成本与收益不匹配。因此按更正是否触及判定，分两类处理：

| 更正类型 | 判据 | 处置 |
| --- | --- | --- |
| **笔误** | 不改变任何发现的级别、判定（CONFIRMED/PLAUSIBLE/REJECTED）、去向状态或报告结论。典型：章节号、路径拼写、错别字 | 可就地更正，但**必须**经作者授权，并在报告末尾"勘误"节逐条留痕（编号、日期、原文、更正后） |
| **实质性更正** | 触及上述任一项。典型：把"已修复"改为"部分修复"、改级别、改判定、改数值 | **不得就地修改**，一律新增补充文档 |

分界的理由：若"已修复"这类**状态标记**也能就地改，那它本身就失去事后可
审计性——任何被漏掉的修复都可以在被发现后悄悄改成"已修复"再补上，痕迹全无。
笔误没有这个风险，因为它不承载任何判定。

判断不清时按实质性更正处理（走补充文档）——多写一份文档的代价，远小于让一次
状态改写变得不可追溯。
