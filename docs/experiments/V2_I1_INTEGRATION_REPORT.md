# V2-I1：第一次系统级集成尝试报告

日期：2026-07-25（2026-07-26 补充连通分量前端与 entity_graph.py
一劳永逸修复后更新）
协议：`experiments/V2_I1_INTEGRATION_PROTOCOL.json`（实现前冻结）
状态：**开发集未通过，一次性留出未消费**

## 目的

这不是能力开发，是"系统级环"能否被验证的第一次真实尝试：把 M2 的
`OnlineEntityGraph`（实体关联+在线控制辨识）和 M4 去特权化的
`UnprivilegedOccupancyMemory`（shadow-casting+对象永久性）组合进
**同一个 agent、同一个世界、同一条按时间顺序的经验流**，用同一次
`update(sensed_occupancy, action)` 调用同时驱动两者。

## 结果

孤立探测器（初次）→ 连通分量前端 → 加宽 `reacquisition_window`
（三个版本依次演进）：

| 门 | 孤立探测器 | +连通分量 | +重识别窗口 | 判定 |
| --- | ---: | ---: | ---: | --- |
| 自我识别 F1（≥0.90） | 0.0000 | 0.0090 | **0.0000** | 未通过 |
| 身份一致性（≥0.90） | 0.154 | 0.197 | 0.198 | 未通过 |
| 干扰物永久性（≥0.55） | 0.538 | 0.538 | 0.538 | 未通过（接近） |
| 去动作对照必须失败 | 未通过 | 未通过 | 未通过 | 自我识别太弱，无法体现下降 |
| 时间打乱对照必须失败 | 未通过 | 未通过 | 未通过 | 同上 |
| assume_all_visible 对照必须失败 | 0.103 | 0.103 | 0.103 | **通过（始终）** |
| 配对分离（≥75%） | 100% | 100% | 100% | 通过（始终） |

自我识别 F1 从 0.009 又回到 0.0000，**不是倒退**——见下文第 5 处
摩擦：加宽窗口后自我 track 的证据轨迹真实地更接近阈值了（一度到
0.49，此前从未超过零星巧合），只是 200 步内始终没能稳定跨过判定
线，这一批种子上表现为 F1 仍是 0。逐个组件看都是真实、可验证的
进展；合起来看，四层摩擦逐一被诊断和/或修复后，第五层摩擦才第一次
可见——这正是分层诊断要做的事。

## 根因诊断（三处结构性摩擦）

**1. 运动尺度不匹配。** `OnlineEntityGraph` 的关联代价函数里
`motion_cost = (distance/0.32)^2` 是为 V2-M2/M3 原生世界的连续、
亚单位位移标定的（`_ACTIONS` 幅度 0.7，且轨迹平滑）。本集成世界用
离散网格、每步整 1 格位移。1.0 的位移距离直接产生代价约 9.8，
高于"判为丢失"的代价（约 7–9），导致算法系统性地更倾向于宣布正常
移动的实体"丢失"而不是正确关联。**已缓解**：把探测坐标按 0.32 缩放后
再喂给 `OnlineEntityGraph`（不修改该已验证组件本身），运动尺度恢复到
其标定区间。

**2. Track 从不过期，长遮挡下失控漂移。** 未匹配的 track 会持续用
自己的 theta/自主速度外推位置，`OnlineEntityGraph` 没有内置的
track 过期或回收机制——这在 M2 原生世界里没问题（遮挡短、探索是
固定循环的 4 动作序列，噪声小）。但在 M4 风格的长遮挡加随机动作下，
仅凭几个带噪样本拟合出的 track 会外推出网格之外、永不被重新关联，
永久占用有限的 track 名额（16 个很快耗尽）。**部分缓解**：在集成层
（不改 `entity_graph.py`）加了越界+长期低置信 track 回收，`n_tracks`
从稳定卡在上限降到个位数，但自我识别仍未恢复。

**3. 孤立探测器在密集网格里频繁失效。** 用于喂给实体图的"3×3 邻域内
恰好一个占据格"孤立性判据，在 11×11 窗口、5 个物理实体（2 静态+3
移动）共存的场景里极不稳定——单帧孤立探测数在 100 帧样本里从 0 到 5
剧烈波动（0:1 次、1:21 次、2:42 次、3:53 次、4:47 次、5:36 次）。
这与 M2 原生世界（物体在连续空间里天然分离，探测数恒定为 3）形成
鲜明对比。频繁的孤立性丢失直接打断身份连续性，RLS 控制证据
（需要连续多步同一 track 才能累积过阈值）从未建立起来。

## 连通分量前端（2026-07-26）

按诊断把孤立探测器换成真正的连通分量分割（`cal.model.integrated_agent.connected_component_centroids`，
8 邻接，6 个单元测试覆盖空探测、孤立点、相邻合并、对角合并、坐标偏移、
密集墙合并成单点）。相邻的占据格现在合并成一个质心探测，而不是像
孤立性判据那样整体丢弃。

效果是真实的：单帧探测数从"0 到 5 剧烈波动"变成稳定的 5–7（100 帧
样本：3 次 3 个探测、37 次 4 个、47 次 5 个、73 次 6 个、36 次 7 个），
且密集的屏风墙第一次被正确地当成**一个**静止 blob，而不是六个
闪烁的单格 track。`self_f1` 从硬性的 **0.0000** 变成 **0.0090**——
仍然远低于 0.90 的门，但不再是零，说明自我发现机制第一次真的有过
零星的正确输出。

## 判断：不再继续打补丁——暴露出了第四处摩擦

连通分量前端解决了它要解决的问题，但没有让自我识别通过。逐步排查
定位到了新的、更精确的阻塞点：

**4. `OnlineEntityGraph._probabilistic_assign` 把超过 6 步未见的
track 视为"不活跃"，直接排除出关联候选**（`entity_graph.py:353-355`：
`active_tracks = [... if self._step - track.last_seen <= 6]`）。
这在 M2 原生世界里是合理的（原生遮挡时长仅 2/23 步）；但本集成
世界里，自我实体因固定相机+遮挡的组合，实测遮挡连续步数最长达到
**10 步**（一次 200 步采样里出现 [4,2,6,1,2,1,1,1,1,10,2,1,2] 这样
的遮挡段长度分布）。超过 6 步的遮挡意味着 track 被彻底放弃、重新
出现时必然创建全新 track——身份从未跨越这类长遮挡存活，这正是
`identity_consistency` 和 `self_f1` 仍然很低的直接原因。

这是同一类问题（M2 假设短遮挡）在换掉前端之后，**从"探测层的噪声"
精确定位到了"关联层的固定窗口"**——诊断精度提高了一层。

## 一劳永逸修复：给 OnlineEntityGraph 加可配置的重识别窗口（2026-07-26）

用户明确选择"修根子"而不是"在集成层外面打补丁"：把第 4 处摩擦的
硬编码 `6` 改成 `OnlineEntityGraph` 的构造参数 `reacquisition_window`
（默认值仍是 `6`，与原硬编码值完全相同）。

**这不是无痛的改动**——`entity_graph.py` 是 M1–M3 综合确认协议
`locked_source_sha256` 锁定的文件之一，编辑它会让协议哈希失效。
按项目纪律走了完整的协议修订流程：

1. **改动前先拍快照**：把当前 M2/M3 开发集产物复制一份留底；
2. **加参数，默认值不变**：`reacquisition_window: int = 6`，
   `_probabilistic_assign` 里 `active_tracks` 判据从硬编码 `<= 6`
   改成 `<= self.reacquisition_window`；
3. **用重跑而不是论证证明行为不变**：改动后用默认参数重新跑 M2
   开发集、M3 开发集（含无因果似然消融），和改动前的快照逐字段
   比对——**除 `cpu_wall_seconds`（计时，非行为输出）外，每一个
   字段完全一致**。这是"默认参数下零行为变化"的实证，不是嘴上
   保证；
4. **新增协议 V4**（`V2_M1_M3_INTEGRATED_CONFIRMATION_PROTOCOL_V4.json`）：
   `locked_source_sha256` 只更新了 `entity_graph.py` 和
   `v2_m1_m3_confirmation.py`（因为需要在 `_load_protocol` 里认
   识新协议状态）这两个文件的哈希，其余 5 个锁定文件哈希不变；
   `amendment_record` 如实记录 `model_or_stage_algorithm_changed: false`
   （对现有调用方而言），但新增字段
   `default_parameter_equivalence_verified: true` 和
   `algorithm_extended_for_new_callers_only: true`，把"没改变行为"
   这句话的证据链交代清楚，而不是简单复用上次的措辞；
5. **`cal-v2-m1-m3-confirm-review` 升级为审计 V1→V2→V3→V4 完整链**，
   新增门验证 v4 修订保留了 v3 协议与一次性确认结果的哈希、
   `fixed_gates` 逐字段相等；
6. **`tests/test_entity_graph.py`（新建）**：5 个测试直接验证默认
   窗口行为、非法窗口拒绝、默认窗口下长遮挡确实丢失身份、更宽
   窗口下同样的遮挡确实保住身份（同一个 track 索引、非重置的
   `theta`）。

修复本身按预期工作：`IntegratedSelfWorldAgent` 现在传入
`reacquisition_window=40`（基于 20 个种子的遮挡时长实测：最长
34 步、p99 约 28 步，40 留出安全余量，不是拍脑袋）。跟踪连续性
从"永久占用 track 名额、身份从未存活"变成"同一个 track 索引跨越
整个 34 步遮挡、置信证据持续增长"——这是可验证的机制改进，不是
换了个说法。

## 判断：第 4 层修复验证有效，同时发现了独立的第五层摩擦

修复后自我识别仍未通过（`self_f1` 回到 0.0000，`identity_consistency`
0.198），但**原因和之前三层完全不同**，插桩证据确凿：

**5. 控制证据的积累速度跟不上这个世界的打断频率。** 直接跟踪自我
track 的 `control_evidence` 轨迹发现：它确实是正确的 track（空间
位置精确对应真实自我坐标），证据也确实在增长（从 0 涨到一度接近
2.0 的判定阈值，对应概率一度到 0.49），但每次自我实体被遮挡超过
3 步，`control_evidence` 就按 0.80 的比例衰减——这个世界里自我
实体被遮挡的时间占比不低（20 种子采样约 17%，且遮挡运行本身可达
30+ 步），导致证据呈锯齿状反复涨跌，200 步内始终没能稳定站上
`self_tracks()` 默认的 0.62 概率门。放宽判定阈值试了一下（0.5→
1.4% 正确率，0.35→2.6%，0.25→4.3%）——确实单调变好，但离 0.90
的门差了两个数量级，说明这不是"阈值卡得太严"，而是证据积累本身
在这个打断频率下太慢，调低阈值是在放松验收标准掩盖问题，不是
修复，因此没有采纳。

这一层需要的是让 RLS 证据积累对"遮挡期间的中断"更鲁棒（比如遮挡期
间冻结证据而不是衰减，或用更长的步数预算），而不是再调一个参数——
按项目一贯的停止纪律，如实记录，移交下一次预注册。

## 这次尝试证明了什么

1. **系统级验证是可执行的**：三次修订前的判断"现有验证手段无法把
   系统级环验证成闭合"不再成立——写了协议、写了度量、跑出了明确的
   通过/失败判定。环从"无法验证"变成了"验证了，而且失败，原因
   明确"。
2. **两个独立验证过的组件不能免验证地拼在一起**：M2 和 M4 各自的
   验证只覆盖了各自原生世界的假设（运动尺度、遮挡时长、探测密度）。
   合并使用会打破这些隐含假设，而这些假设此前从未被写下来过——
   本次集成把它们变成了显式的、可检验的事实。
3. **换前端确实推进了诊断，但没有让协议通过**：连通分量分割修好了
   它该修的问题（探测数从 0–5 的噪声变成稳定的 5–7，`self_f1` 从
   硬性 0 变成 0.009），随即精确暴露出下一层摩擦（M2 的 6 步不活跃
   窗口假设短遮挡）。这印证了第 2 点的结论：每一层"合理的下一步
   修复"揭开的都是新的、真实的隐含假设冲突，不是同一个问题反复
   出现——集成层面的困难是分层的，需要逐层诊断，不能指望一次
   修复解决。
4. **"一劳永逸"修根子和"逐层深挖"这两件事互不矛盾**：给
   `entity_graph.py` 加可配置窗口是真正的一次性、可复用修复（任何
   未来复用 `OnlineEntityGraph` 的调用方都能受益，不像坐标缩放/
   track 回收那样只对这一个探针生效），而且用重跑逐字段比对而不是
   论证证明了对现有验证链零风险。但修根子并不意味着协议会通过——
   它精确解决了自己诊断出的那个问题（身份不再被长遮挡摧毁），随即
   诚实地暴露出下一层、性质完全不同的摩擦（证据积累速率）。四层
   摩擦累计下来的规律很清楚：**每次修复都是真实的、可验证的进展，
   但集成两个独立验证组件的困难本身是分层的，不存在"修一次就全部
   解决"的单点修复**。
